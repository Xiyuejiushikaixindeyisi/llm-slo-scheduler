同日后续更新：用户已提出GF普通FIFO＋让行LIFO为主候选，详见[GF方案讨论](GF_SUPER_P95_DESIGN_DISCUSSION.md)。本机已核对Motor f203263d具有请求token化与Conductor分层前缀查询；本文第5节的body/4限制只描述现有FGJSQ绑定路径。下文保留证据整理时的候选比较，最新研究方向以上述讨论为准。

研究目标保持全体请求P90 TTFT改善、吞吐提升或不下降、P90 TPOT满足SLO，P95及被延后请求的损害作为补充。主指标不能只算普通队列，也不能把GF新增等待排除在客户端计时之外。

## 3. super-p95要拆开的机制

| 原型组件 | 可参考的思想 | 迁移时必须区分 |
| --- | --- | --- |
| 有预算地标记高成本请求 | 让少量请求承担有界的额外等待，以交换更多请求的早入场机会 | 原型累计分类额度不直接限制队列长度、最长等待或资源存量；不能直接照搬5% |
| 普通队列优先 | 将分类真正兑现为下一次执行机会 | 两条容器本身无收益；需要有可执行候选和可分配资源 |
| diffusion step边界暂停让行请求 | 让已经开始的长任务也能让出后续机会 | 这与LLM“只改变首次入场”不同；running/KV处理目前pending，不能暗中包含进双等待队列 |
| 让行队列LIFO | 原型的一种取序方式 | 可能延长旧请求等待，不是迁移必需条件；FIFO/老化等候选下一轮讨论 |
| 路由中让行负载折扣 | 改变分类请求在后端间的分配 | 与FGJSQ保留完整负载的反馈不同；不可未经设计直接折扣或提前释放 |

**当前机制假设**：当同一决策边界存在多个可执行等待请求，且预计新增工作量或紧迫程度不同，有界地推迟部分请求，可能让其他请求更早获得入场机会。是否改善全体P90且不损吞吐，尚未被两份报告证明。

不能提前宣布原型“真正有效的唯一机制”已经定位。现阶段可明确的是：分类、预算和执行优先级共同构成机会分配；原型的step暂停使优先级能在已运行任务上兑现。只移植首次入场时，这部分能力不会自动继承。

## 4. 把“让行”与“本来不能执行”分开

讨论候选状态可包括：普通等待、策略主动让行、资源/远端KV尚未就绪、已running。最终是否使用独立容器由实现方案决定；此处只是避免语义混淆。

- 策略让行：本来具有可执行机会，却因策略选择暂时不入场。
- 资源阻塞：token/序列/KV/connector等条件不满足；不是主动让行带来的等待，也不应盲目消耗相同预算。
- 已running：后续chunk能否让出预算是另一层问题，当前不自动纳入。

running-first意味着waiting只得到本轮剩余预算；若本轮根本没有可分配资源，仅重新排列waiting不能制造入场机会。反之，有足够资源而策略使其闲置，也不能直接宣称吞吐保持。即便工作守恒，批效率、缓存演化和开销仍会变化。

## 5. 请求分类：讨论的是决策时可知信息

| 信息 | 当前作用 | 需要保留的边界 |
| --- | --- | --- |
| P已tokenize的prompt长度 | 基础输入特征 | 不等于uncached或剩余服务时间 |
| GF当前body/4估计、账本负载 | 粗略路由与初始存量 | 首个批事件才校正；尚未入场请求未必得到校正 |
| 当前真实可得的本地/外部prefix命中 | 若决策路径能取得，可改进工作量估计 | 查询时间/状态副作用/失效可能性仍属设计约束；R1最终cached不能倒填 |
| 请求年龄、已被越过次数、让行队列驻留 | 保护已等待请求 | 队列年龄不等于相对FCFS的因果额外等待 |
| 历史长度/命中统计 | 可讨论为先验或置信度来源 | 不能泄漏当前请求事后信息；租户仅因成本高不应自动降级 |
| batch predictor | 可作为批级候选成本线索 | 标签是主机观察间隔，legacy cache_hit_rate非真实APC；不能直接充当请求剩余TTFT |

下一轮可以比较“成本分类”“紧迫程度与成本结合”“低置信度时少让行”等候选，但本轮不决定特征权重、阈值或优先级公式。

## 6. 让行预算至少分四个问题

| 预算/保护 | 需要回答的问题 | 两份报告不能给出的答案 |
| --- | --- | --- |
| 分类额度 | 在多长窗口内允许多少请求进入让行类，何时补充/消耗？ | 不能从P90的10%或原型5%直接取值 |
| 等待存量 | 同时延后多少请求、多少预计工作量/资源需求？ | FG账本remaining不等于让行队列长度和存量 |
| 时间/越过次数 | 多久或被越过几次后恢复正常竞争？计总年龄还是进入让行类后的驻留？ | 历史waitproxy最大值与SLO都不是安全额外等待预算 |
| 最低进展 | 何时保证延后类别重新获得服务机会，如何处理不具备资源资格的请求？ | 5% retention不提供服务保证；恢复优先权也不等于无条件立刻入场 |

原型分类比例、FGJSQ的5%剩余负载保留、业务P90的10%尾部分位是三个不同概念。最大等待、最大队列存量和最低进展需要独立讨论，不能用一个比例代替。

如果优先请求持续到达且资源长期不足，老化或强制恢复优先级不能无条件保证硬时限；先明确承诺的是选择规则还是时间SLO。具体数值待算法讨论与后续授权实验，不从这两份材料虚构。

## 7. GF/P放置要比较三种时点

| 候选位置 | 能控制什么 | 主要约束 |
| --- | --- | --- |
| GF选择/预留P之前 | 集群级释放请求、然后再路由 | 本地P就绪状态较间接；需表示GF待释放存量，不能假装这些请求已经在P账本里 |
| GF已经预留P、转发之前 | 已绑定P的释放时机 | native/FG预留继续占用，可能影响路由和名额；客户端取消、过期、释放必须保持一致 |
| P引擎首次入场之前 | 本P可执行候选的优先级和实际准入 | 受running-first、资源检查、异步已提交批限制；保留Ascend/async链和原生生命周期 |

R2只举了GF reserve之后的例子，不能因此排除reserve之前。本文不替用户选址；下一轮先明确要控制的机会范围，再比较信息与工程成本。

将等待挪到GF会改变引擎queue_time，但客户端TTFT必须包含该等待。不能把引擎队列变短本身当作优化成功。

## 8. FGJSQ＋predictor的兼容约束

1. 尚未首次调度通常无批事件，FG原始预留继续存在；延后入场会反馈路由，不是独立于路由的局部改动。不要伪造scheduled=0完成事件或打折隐藏存量。
2. 事件保持请求/attempt/epoch身份和单调性；snapshot冻结计划状态，computed不冒充NPU完成量。
3. native配额释放与FG账本释放分开；后者现有触发是D首个非空body bytes，不能改成P首次入场或“加入让行队列”。取消/失败清理应覆盖新增等待状态。
4. g5旧SLO入场开关非零即拒绝。未来方案应独立设计开关与回退，不把打开旧开关当作新算法。
5. predictor只承担已定义的批级估计；如果用于分类/预算，需在讨论中明确组合规则、置信度和误差处置。D引擎和D路由保持基线。

上述是设计约束，不表示已批准实现。既有[src](../../src)保持不变，本轮不生成代码包。

## 9. 下一轮讨论顺序与已接受未知

建议按以下顺序收敛，而不是再采集流量：

1. **机制范围**：先限定只改变首次入场时，我们希望哪类请求让出什么机会？哪些super-p95能力主动不迁移？
2. **分类规则**：如何结合可知成本、等待年龄、候选差异和置信度？同质/无竞争时如何回退？
3. **预算和保护**：分类额度、队列存量、驻留/越过次数、最低进展之间如何约束？
4. **放置与反馈**：GF预留前、预留后、P入场前哪个最符合目标，如何保持FG账本和取消一致？
5. **可检验主张**：明确目标改善、可能受损的群体及吞吐/TPOT约束，之后再讨论实现和实验审批。

接受但不继续追索：九字段单位与completion语义、逐请求阶段分解、同P同时候选的完整历史、设备容量、g5高压性能、真实在线cache可见性的所有细节。未知不是正面证据；算法讨论使用条件假设，不默认ρ≈1、不默认66k存在4.2s running等待、不承诺收益。后续只有用户明确要求时才重新开启对应调查。
