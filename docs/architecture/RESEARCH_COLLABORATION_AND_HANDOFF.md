## 2. 研究目的与两条研究线

最终目标是在**现网流量下提升单卡吞吐、优化尾延迟**。研究单位为一个 `instance_uuid` 对应的 GF＋XPYD 集群。高并发 AISBench 是极端压力验证场景，用于比较相同负载下的 P90 TTFT，或相同 TTFT/TPOT SLO 下可承载的并发；不能直接将闭环收益等同于生产开环收益。

| 研究线 | 决策问题 | 主要目标 | 当前边界 |
| --- | --- | --- | --- |
| 入场与让行 | 谁获得下一次入场机会，哪些请求让行、允许让行多少 | 降低全体请求 P90 TTFT，P95 为补充，吞吐保持或提升 | GF 双等待队列；首次入场前决定；P 引擎调度语义保持 g5 |
| batch/chunk 寻优 | 根据状态给下一批多少执行量，如何选择 chunk/token/batch size | 提升吞吐，同时满足延迟约束 | 先数学建模，由 Session 3 负责；不随首版 GF 插件修改引擎 |

有预算地延后部分请求是候选机制，收益仍需实验确认。统计必须保留让行请求及其完整 GF 等待，并同时报告失败、取消、未完成请求，不能只展示普通队列的尾延迟。引擎侧 waiting 重排、保留/释放 KV 的抢占仍为 pending。

吞吐报告注明请求/s、输入或输出 token/s、有效 SLO 内吞吐等实际口径，以及使用的 P/D 卡数与时间窗；单卡口径明确分母。不能假设当前平均吞吐已经接近硬件容量。

## 4. 本机与华为机的职责

| 环节 | 本机 | 华为实验机 |
| --- | --- | --- |
| 研究与设计 | 源码调研、机制判断、方案与接口设计、制定实验问题 | 提供已有现场事实及实现约束 |
| 代码与验证 | 编写/修改代码，单元测试、确定性重放及适用的接口/集成测试；记录未覆盖的真实栈条件 | 在目标镜像、权重、910B2 集群中部署、debug、完成真实栈集成验证 |
| 交付与执行 | 准备版本化代码包、运行 prompt、启用/关闭/回退方法 | 按 prompt 执行；遇到适配问题可现场修复，但须完整记录差异 |
| 压测与数据 | 规定对照、指标口径与判定目标；分析回传结论 | 执行冒烟和完整压测，保留原始材料，回传有证据的结果文档 |
| 迭代 | 核对现场修改，吸收或修正到本机，再设计下一轮 | 验证下一版包并报告与上一版的变化 |

**本机负责设计与迭代决策，华为机负责现场执行与实证。** 本机不能直接读取内网代码、完整结果和原始日志。因此本地测试通过不能写成现场验证通过；报告中的描述也不能自动当作已完成远程逐文件校验。

协作顺序：本机交付代码＋prompt → 华为机部署/debug/实验 → 华为机回传自包含 Markdown → 本机归档、核对源码差异与结果、更新上下文 → 本机修改并交付下一版。现场必要修复不能只留在内网；后续本机包要明确吸收哪些修复，避免覆盖它们。

交付压缩包先在 WSL 项目中准备并校验，再按既有约定移动到 Windows 桌面；研发源码和研究文档保留在项目内。没有本轮交付任务时不生成包。

可以只回传一份 Markdown，文件名应能区分运行或版本；不要求完整目录、模型、完整代码库或所有原始日志外传。**关键源码和证据直接嵌入正文，内网路径仅作为来源索引。** 报告已有足够依据时不为补齐格式追加实验；无法提供的内容明确写“未记录/未核实”。

| 正文内容 | 需要说明什么 | 本机据此做什么 |

| 实验清单 | run_id、时间/时区、命令或配置、数据/长度/并发/压力时间、成功/失败/取消/未完成数；重启、热身、缓存及在线训练是否延续 | 判断对照是否可比、是否存在状态继承 |
| 结果与来源 | 基线与候选的 TTFT/TPOT 分位、吞吐及单位/样本数/统计口径；关键原始摘要、计算方式、日志摘录 | 判断尾延迟与吞吐是否同时改善，避免只看成功子集 |

## 6. 数学线进度备忘

以下是**用户本轮报告的研究进度**，本会话不重新验证消融实验或推导。用户指出 batch size 与到达率、请求长度、已入批 token、待处理 prefill 请求数和等待 prompt token 总量有关，已做第一版建模与权重优化。模型 1.0 为用户自建公式：

\[
C_* = \underset{C}{\arg\max}\left(
\frac{C+\sum p_i+\sum w_j+\lambda T_{mix}(d_1,\ldots,d_k;C,p_1,\ldots,p_m)\mathbb E(L)}
{T_{mix}(d_1,\ldots,d_k;C,p_1,\ldots,p_m)(1+m+n)+\lambda T_{mix}(d_1,\ldots,d_2;C,p_1,\ldots,p_m)^2/2}
\right).
\]

保留两个时间函数中 `d_1,…,d_k` 与 `d_1,…,d_2` 的区别，用户已明确它不是笔误。符号含义、两种状态的解释和数学有效性继续由 Session 3 维护，不在本会话猜补。

当时的下一步方向是把 batch-level TTFT 预测器映射到成本函数，再研究如何用微分方程联结微观 cost function 与宏观 KV cache 状态，联合求解 chunk size。这是研究计划，不是已完成的微分方程或已验证的吞吐收益；10 月 29 日当前工作顺序见文末，完整 KV 联合模型不作为首版前置条件。现有 predictor 实际标签与数学所需服务时间的差别须保持明确；不得因引入新模型而无版本区分地修改 g5 predictor v1。
