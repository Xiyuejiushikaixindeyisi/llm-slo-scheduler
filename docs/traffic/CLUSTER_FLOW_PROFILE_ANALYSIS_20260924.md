## 3. 原文中需要单独纠正或保留疑问的地方

### 3.1 延迟未知不能读成零违约

`resolved_input_units`两项都是unknown，TTFT/TPOT有效数均为0；总体及分组中`ttft_slo_violation_n=0`是空有效集合的计数结果，不表示实际没有违约。`ttft_tail_n=0`同理。P90、P95、SLO达标率、尾部组成、前10s工作量与尾部的关联，本批均未得到结论。

报告的`metric_units`为脚本目标输出单位，不是数据库单位已确认的证据。1194–35489和2–31这两个原始范围也不足以直接定单位。本机不据此猜测TTFT为ms或TPOT为ms。

因此原文“可以支持的下一步讨论”中涉及“尾部构成及其关联”的句子是工具能力说明，不能当成本次已完成的分析；F5的“唯一功能缺失”也不精确，因为输出token统计同样存在系统性口径问题。

### 3.2 completion_tokens语义必须保持未决

5,548/5,549条出现completion<prompt（约99.98%）。这足以说明“该导出字段=输入＋输出”与样本系统性不相容，不能当作零星坏行。它可能实际代表输出token，也可能导出映射有误；仅靠数值形状不能裁定。

按减法算出的唯一一条output_tokens=1,566，也只是该假设下的结果，不宜作为已核实输出样本。因此当前不使用输出分布、D工作量或推算E2E/在途数。输入和cached的独立统计不因此被全部丢弃。

### 3.3 completion≥8192不是由组批预算推出的异常

本项目当前的8192指每轮组批token预算。锁定vLLM v0.23.0源码中：

- `vllm/config/scheduler.py:49`定义`max_num_batched_tokens`为单轮处理token上限；`:56`另有单轮可调度token上限；`:84`说明chunked prefill按剩余预算分块。
- `vllm/v1/core/sched/scheduler.py:360`在每轮初始化token_budget；`:410`和`:699`裁剪本轮分配；`:516`和`:844`扣减本轮预算。
- `vllm/sampling_params.py:261`的`max_tokens`才是每条输出序列的生成上限，是另一参数。

因此单请求跨多轮可以累计处理/生成超过8192 token；没有另行确认的请求级上限时，completion=16,384或大于prompt不能仅凭8192判异常。原文C-1把这称为“两种解读都冲突”的硬异常，应撤销。字段语义冲突仍存在，不能因为这一纠正就反过来认定所有completion取值都正确。

依据：[固定commit的SchedulerConfig](https://github.com/vllm-project/vllm/blob/0fc695fc6d1d82e9a5ac6835ac8e4e1c83703665/vllm/config/scheduler.py#L49)、[固定commit的采样参数](https://github.com/vllm-project/vllm/blob/0fc695fc6d1d82e9a5ac6835ac8e4e1c83703665/vllm/sampling_params.py#L261)、[vLLM v0.23.0官方chunked prefill说明](https://docs.vllm.ai/en/v0.23.0/configuration/optimization/#chunked-prefill)。本机也核对了上述commit的本地源码；这用于解释参数，不替代现场配置核验。

### 3.4 九个UUID并不反证“一个UUID对应一个集群”

用户在本会话提供的原SQL只按模型规格和request_time筛选，没有`instance_uuid`条件，天然可能导出多个同规格集群。报告C-3把九个UUID视为与字段粒度矛盾，证据不足；请求数或长度分布相近也不能推翻集群标识语义。

继续按用户已给定义分集群分析，明确报告只选一个UUID。实验机以历史EXP_10.9重放可比性选该UUID，是执行侧选择，不是随机抽样；不能外推为九集群整体或现网普遍规律。其余UUID的7.22次/s也不能用于当前单集群负载判断。

## 4. 对super-p95双队列的具体含义

### 4.1 本批支持研究“谁更昂贵”，尚不支持判定“谁阻塞了谁”

原始长度、未命中token、预计批成本应分开。长输入高命中请求可能只有少量新token需计算；高命中也不保证总执行开销等同短上下文请求。应研究**决策时能够获取的预计新增工作量及其不确定性**，并结合等待年龄和当前系统状态，不把长prompt、零命中或某个租户直接等同低优先级。

实际cached是原策略执行后的日志。GF或P在入场时能否看到命中、改变路由/顺序后命中是否变化，本报告均未证明。离线实际命中可用于说明分类机会，不能作为在线oracle直接填给算法。已有batch级predictor也不是逐请求剩余TTFT预测器，本批报告没有新增证据证明它能直接输出请求排序分数。

### 4.2 双队列的候选机制是有限让行带来的入场机会转移

值得验证的机制假设：当多个可执行请求同时等待，而且预计新增工作量差异较大时，对部分高成本请求施加**有界的额外等待**，让其他请求更早获得入场机会，从而改善全体请求的尾部指标。双队列只是实现这种选择的一种结构；有效性不来自“分成两条队列”本身。

本批已展示群体成本异质性，但没有同一P同一时刻的候选集合、首次入场等待或服务时间。因此尚未证明可让出的入场机会、真正的阻塞关系，更没有完成super-p95各模块的消融归因。

保留首次入场与running续算边界：若长prefill已经running，而主要延迟产生在之后的连续分块执行中，仅改变尚未入场请求的队列不能直接消除这段延迟。GF/P放置仍待讨论；不因为GF可见租户就先定GF，也不因P有cached字段就假定该值在选候选之前可用。本轮仍不引入waiting重排、running/KV抢占、LIFO或动态chunk。

### 4.3 预算需约束伤害，不能从请求占比直接设定

≥32K零命中组约22.85%的请求，明显超过P90右侧名义10%的尾部份额。这个比较不能直接推导最佳预算，但提醒我们：不能把整组长期延后，并期待这些请求都“藏在P90之外”。即使某策略只延后不到10%的请求，也不自动保证P90改善，P95/P99、超时和租户公平性仍可能恶化。

后续讨论可分三类预算，当前不确定数值：

| 预算 | 想控制的风险 | 本报告能提供什么／缺什么 |
| --- | --- | --- |
| 等待存量：低优先级队列长度、累计预计未完成工作量 | 高成本请求持续堆积，单靠请求数低估负担 | 提供工作量异质性；没有实际队列轨迹，不能定容量 |
| 时间与越过次数：最大额外等待、允许被多少次入场选择越过 | 饥饿、SLO及租户损害 | 单位和入场等待未知，不能从27s直接减出安全让行时长 |
| 服务机会：为延后类别保留最低进展机会 | 高成本工作长期得不到处理、积压不消退 | 提供类别占比；没有服务率或批组成，不能换算让行比例 |

吞吐保障要在实验中独立验证：除确认具有可执行候选外，还要观察组批效率、缓存演化、调度开销和实际完成量。仅保持工作守恒也不能承诺LLM批服务吞吐不变。稀疏或候选成本相似时，优先级选择的空间可能很小；这是场景假设，不由0.77次/s就能判定当前系统稀疏或拥塞。

### 4.4 场景选择与建模用途

当前已有材料足以继续机制讨论，不需要先完成M/G/1拟合。最小建模对象是带输入长度、实际命中等标记的**处理起点序列**；后续若有原始trace，优先保留其时间变化和标记关联，不把0.77、Fano和两个均值当成完整生成模型。这些摘要并不唯一决定请求的联合分布或相关性。

建议讨论的对照包括：同长度不同命中、短低命中与长高命中、计数峰与工作量峰分离、成本同质且排队少的对照场景。07:25/08:57只是候选片段，不是已确认的策略最优场景。单UUID两小时样本不代表其他时段、128K规格或闭环AISBench。
